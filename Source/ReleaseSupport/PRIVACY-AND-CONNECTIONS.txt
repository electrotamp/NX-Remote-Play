NX-Remote-Play beta: connections and diagnostic logs

The native remote-play connection uses a Session ID and join password. This beta sends these credentials without encryption on its native rendezvous paths. Someone able to observe those messages could obtain them and potentially join the session. First-use desktop ownership setup also sends a password-derived proof that an observer could use to test password guesses. Credential protection is deferred to a later build. Browser HTTPS connections use a separate path; this statement does not certify their security.

On Android 10 and later, finishing a stream can save a diagnostic ZIP in Downloads/NX-Remote-Play. Desktop support reports and server logs can also contain session IDs, IP addresses and other diagnostic details. Review logs before sharing them. Older logs may retain connection tickets even after updating to this beta. The Android ZIP exporter writes to local storage; automatic backup or synchronization by other software is outside its control.

Every app can also save its own logs in one file for a problem report. The Switch app (Settings, Export logs) writes NX-Remote-Play-logs.txt to the SD card root; Android (Settings, About, Export logs) saves a ZIP in Downloads/NX-Remote-Play; the desktop app (Settings, Diagnostics, Export logs) saves a ZIP in its Diagnostics folder; the web page (Export logs) offers a text file or the phone's share sheet. These apps never send the file anywhere: you decide whether and where to share it. The console's support log leaves out passwords, Session IDs and IP addresses, but its developer logs, the Android and desktop logs and the desktop connection traces can contain network addresses and identifiers. Connection tickets are blanked in the Switch and Android exports; desktop exports are not filtered. The web log holds no tickets, passwords, Session IDs or server addresses. Look through any log before posting it publicly.

When the Windows app finds a plugged-in Switch with no USB driver, it downloads Google's Android USB driver from dl.google.com, checks its SHA-256 and installs it after a Windows permission prompt; dl.google.com sees the requesting network address. Nothing else is downloaded by the app.

Each time it starts, every app (Windows, Android, the Switch app and the web page) asks GitHub's public release list at api.github.com whether a newer version is out; Settings has a button to check again. The request carries no Session ID, password or log, only the app's name and version; GitHub sees the requesting network address. The apps only show the result and a link to the releases page: nothing is downloaded or installed automatically.

Desktop public-browser sharing uses api.ipify.org to discover this computer's public IP address; the service sees the requesting network address. Optional automatic browser certificates contact Let's Encrypt when enabled and accepted. Configured rendezvous servers, peers and STUN services receive the network traffic needed for their roles.

This describes reviewed behavior. It is not a complete dependency or network-traffic audit. See the package README for installation and verification status.
